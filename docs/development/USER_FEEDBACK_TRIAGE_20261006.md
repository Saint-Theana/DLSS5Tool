# 用户图片与预览交互反馈排查（2026-10-06）

| --- | --- | --- |

## 1. 透明 PNG

涉及 `dlss5tool/gui.py`：

- `_read_image_bgr` 使用 `cv2.IMREAD_COLOR`，读取阶段就将四通道 PNG 变成三通道。
- `_load_image` 只保存 `_image_bgr`；当前没有保留原始 alpha 的旁路。
- `_process_still_image` 通过 `COLOR_BGR2RGBA` 补回的 alpha 全为 255，返回值再次去除 alpha。
- `_export_image_source` 重新调用同一读取函数，最终写出三通道图片；因此不只是预览底色问题。

内存 PNG 复现：输入 alpha `[0, 0, 128, 255]`，生产读取函数返回三通道，
用模拟推理器接收生产处理函数的输入时 alpha 为 `[255, 255, 255, 255]`，
处理结果编码成 PNG 后用 `IMREAD_UNCHANGED` 解码仍为三通道。
全透明黑色像素变成不透明黑色；全透明彩色像素会显露原来隐藏的颜色。
本测试只模拟推理器，不代表验证了真实模型的透明边缘行为。

建议：读取时独立保存 alpha，预览用棋盘格或可选底色合成，推理只处理颜色，
输出 PNG 按输出尺寸恢复 alpha。还需验证半透明边缘、超分后蒙版缩放及黑边/色边，
不能只把 `IMREAD_COLOR` 改成 `IMREAD_UNCHANGED` 就认为完成。
JPEG 等不支持透明的输出应显式选择底色或提示。
图片序列是另一个输入契约：`image_sequence._decode` 当前明确拒绝四通道，不能误称其已支持。

## 2. 右键拖动画面与手势冲突

`App._create_preview_pane` 只绑定左键按下/移动/释放，没有右键拖动绑定。
`on_canvas_press` 的优先级为导航小图、分隔线附近或 Shift、放大后的平移、普通点击/对比拖动。
分隔线命中范围是左右各 18 像素，并非只允许抓住可见的 2 像素线。

隔离调用生产事件处理函数确认：

- 适应窗口、远离分隔线：进入对比拖动。
- 放大后、远离分隔线：进入平移。
- 放大后靠近分隔线，或按 Shift：进入分隔线拖动。

建议新增右键拖动平移，让左键对比操作更明确；兼顾已有左键习惯，不必直接移除旧手势。
无移动的右键点击不应切换播放。需覆盖停靠、独立窗口、全屏和放大状态。
改按键本身不会消除显示重绘开销。

## 3. 视频发灰与进度

`App._pending_preview_image` 主动执行灰度转换，并只保留 28% 亮度。
`_blit_play_split` 在结果缺失且 pending 时用此图替代处理侧；普通播放预览的结果缺失路径也会使用它。
因此等待时发灰有明确代码来源，不等于最终超分颜色异常或 GPU 死锁。
并非所有等待路径都会发灰：部分暂停/原图预览仍显示正常原帧。

已有反馈：

- 导出：`set_progress` 更新进度条、帧数、速度和预计剩余时间，不能归类为完全没有进度。
- 普通预览：时间轴缓存区间及当前帧/前向缓存状态。
- 超分/插帧共享预览：`_shared_display`、`_shared_buffer` 显示准备/缓冲第几帧，
  `_shared_paint` 在结果就绪时展示已缓存帧数。

缺口：共享预览没有接入渲染会话的阶段进度回调；初始化和首帧推理阶段可能长时间停留在
同一条准备/缓冲文本。`RenderSession.progress` 默认为 None，导出会调用 `set_progress`，
而预览适配器没有对应接线。界面已有首帧就绪后展示的路径，不需要等整段视频全部处理完。

建议：保留正常原帧（或明确标记的旧结果），叠加动态忙碌提示、当前阶段和已等待时间；
能够计量时显示完成帧数/缓冲量，未知初始化阶段不伪造百分比。
保留逐帧就绪即显示，提供暂停/取消或关闭预览入口。不要承诺所有硬件都能实时超分播放，
也不要把按需预览的缓存窗口百分比冒充整段视频导出进度。

## 4. 分隔线重绘性能

生产调用链：`on_canvas_drag` → `_update_split_from_event` → `_blit_split`。
即使帧内容、缩放和平移都没变化，每个拖动事件仍会对原图和结果图执行视口缩放，
复制合成图、转换颜色、创建 PIL/Tk 图像、删除并重建画布元素。
没有拖动事件合并，也没有针对仅分隔位置变化的视口栅格缓存。
现有显示手势会保留后台推理工作，并非每次拖动都重新启动推理。

内存探针：120 次生产 `_update_split_from_event` 调用触发 240 次 `cv2.resize`、
120 次 `PhotoImage` 构造入口。合成帧对，每项预热 5 次、测量 25 次：

| 原图及结果尺寸 | 预览尺寸 | 中位耗时 | P95 |
| --- | --- | --- | --- |
| 1920×1080 | 1280×720 | 3.96 ms | 4.28 ms |
| 3840×2160 | 1280×720 | 4.54 ms | 4.80 ms |
| 7680×4320 | 1280×720 | 8.51 ms | 8.96 ms |
| 3840×2160 | 1920×1080 | 6.68 ms | 7.18 ms |
| 7680×4320 | 3840×2160 | 24.53 ms | 25.53 ms |

测试调用实际 `_blit_split`，但将 Canvas 绘制、PhotoImage 上传和标签/导航图绘制替换为空操作。
因此数字仅为本机 CPU/PIL 部分成本，不是端到端鼠标延迟或用户机器帧率。
OpenCV 报告 20 个线程；没有 GPU 并发负载。

建议缓存当前帧在当前视口下的两侧图像，仅在帧、尺寸、缩放、平移、参数变化时失效；
按显示刷新节奏合并鼠标事件并采用最新位置，减少整幅图像上传及 Canvas 元素重建。
保持现有“不停止播放、不重启推理”的约束，同时单独优化左右键职责。
