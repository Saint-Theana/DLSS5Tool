## 一、已落地的代码

- `dlss5tool/adapter_inventory.py`：保存原有适配器结构、身份转换、DXGI/CUDA 查询；纯结构可在主进程使用，原生查询只由探测进程调用。
- `dlss5tool/adapter_probe.py`：一次性子进程、私有继承管道、有界 JSON、协议/nonce/PID 校验、并发合并、缓存防御性副本和失效代次。缓存按宿主路径、大小和修改时间区分，显式刷新重新探测。
- `dlss5tool/process_job.py`：仅持有本次 `Popen` 的进程句柄，将子进程加入 kill-on-close Job 后才允许开始原生查询。超时/取消/退出失败保留进程、管道或 Job 所有者，退休成功前不创建下一次探测。
- `dlss_engine.py`、`residual_composition.py`：GUI、NR 选卡和合成查询统一走隔离入口；保留原有物理显卡 ID 与 LUID/PCI 匹配。实际显卡不匹配时失效列表并报告选卡错误；legacy/可选宿主无 v2 列表时仍支持返回实际设备元数据。
- `dlss5tool/gui.py`：刷新显卡列表触发真实刷新；关闭时阻止新扫描，回收探测进程并等待扫描线程，失败保留窗口供重试。
- 根 `gui.py` 与 `dlss5tool/__main__.py`：在 GUI/安装互斥初始化前分派内部探测入口，支持源码和冻结程序。

探测采用 `subprocess`，可在既有 daemon NR worker 内使用。源码使用同版本基础解释器和 `-I -S -B`，避免 Windows venv redirector 增加中间进程；冻结版复用可执行文件的内部入口。已有处理 worker 和资源交接继续复用。

代价是首次/显式刷新约 3 秒；缓存命中约 0.2 毫秒。查询失败会给出明确错误，不会将未知结果当作没有显卡。

## 三、实际内存验收

私有提交均来自被观测任务的精确进程身份；进程树总量单独报告，不混入无关后台应用。系统余量用于安全保护，不用于把其他应用的内存归给本项目。

空闲曲线排除前 10 秒，连续处理排除前 60 秒；以五个分窗中位数记录变化。事先登记的平台门槛为：前后中位数差和分窗中位数范围各不超过 16 MiB，斜率绝对值不超过 0.25 MiB/分钟。GUI 在两轮预热后按三种尺寸分别比较，私有提交差不超过 16 MiB、Python heap 差不超过 8 MiB、Tk 图像数稳定。有限窗口通过不等于原用户小时级验收。

| 用例 | 观察 | 结果 |
| --- | --- | --- |
| 修改前本地合成器 | 首帧后空闲 60 秒，私有提交约 +64.01 MiB/分钟 | 增长 |
| 隔离后本地合成器 | 首帧后空闲 300 秒，约 −0.105 MiB/分钟；默认原生堆约 +99.5 kB | 本轮空闲门槛通过 |
| 隔离后 VSR | 首帧后空闲 300 秒，约 +64.48 MiB/分钟 | 平台未通过 |
| 隔离后 NR | 首帧后空闲 300 秒，约 +68.20 MiB/分钟 | 平台未通过 |
| 同一 GUI 30 次图片轮换 | 三种尺寸均出现相同尺寸基线持续抬高，Python heap 和 Tk 数量基本稳定 | 处理/导出/清理/退出完成，平台未通过 |
| 隔离后连续合成 | 30 分钟完成 83,375 帧；预热后约 +0.073 MiB/分钟，中位数差约 +1.68 MiB | 本轮连续处理门槛通过 |

处理/退出通过不代表内存平台通过。已结束的正式用例无安全阈值停止、无 supervisor 强制回收、最终无遗留进程；每条隔离后正式用例记录运行前后源码/运行库哈希。修改前 60 秒基线只有当时源码快照和参数，没有后来加入的前后完整 manifest；两组观察窗口长度不同。

GUI 按同尺寸比较第 7→28、8→29、9→30 次图片（事件 `cycle` 从零计）：私有提交分别增加约 315.6、314.5、311.6 MiB；对应 Python heap 各只增加约 0.106 MiB，Tk 图像数均为 296，来源/输出缓存账目按尺寸稳定。这不能解释全部原生增量，尚未取得 GUI 分配调用栈的独立归因。

连续合成的预热后五窗中位数范围约 1.68 MiB，后半段五窗范围仅 4 KiB；进程树峰值约 209.4 MiB。原生堆首帧到最后快照约增加 1.08 MiB，预热后前后窗口中位数差约 43.2 KiB。完整首尾匿名私有提交快照约增加 19.88 MiB，包含前期阶跃，不能与排除预热后的分窗差混用。上下文创建/销毁为 1/1，最终设备引用为零。

长测期间源码/运行库前后哈希一致。长测结束后仅删除了 `_selected_render_adapter()` 中相邻重复、不可达的 legacy 返回分支；保留原测量源文件、最小补丁、前后哈希并做 AST 对照，确认无其他语法树变化，随后 65 项选卡/隔离/合成回归通过（已包含在上述去重数内）。测量版本与最终文件的这处差异明确记录在 `post-acceptance-source-cleanup.json`，不隐写为完全同一哈希。

较早的长时 pilot 在约 754 秒因最终兼容性/取消入口收尾而主动中断；其 `result.json` 仍为失败，`controller-stop.json` 解释排除原因，未计作 30 分钟验收。

### 追加的独立原生对照

`native_graphics_memory_probe.cpp` 不使用 Python、NGX 或项目处理运行库。四组均观察 60 秒，排除前 10 秒；完整参数、源码/二进制哈希、PID/创建时间、实际适配器、模块列表和每秒内存见证据。四组均正常退出，设备最后释放引用数均为零。

| 原生控制 | 私有提交斜率 MiB/分钟 | 默认原生堆斜率 MiB/分钟 |
| --- | --- | --- |
| 单个 D3D11 设备 | +0.108 | +0.036 |
| CUDA 初始化＋单个 D3D11 设备 | +83.53 | +77.38 |
| 同时两个 D3D11 设备 | +0.028 | +0.013 |
| D3D11 设备创建/释放 10 轮 | +0.068 | +0.037 |

这些短测与长时合成同时运行，仅用于触发条件筛查，不比较吞吐，不满足五分钟/小时级平台口径。所有组仍加载 `nvspcap64.dll`；这不能证明其 hook 状态，也不能排除覆盖层的影响。该对照复现 CUDA＋D3D 的持续增长，但未证明 GUI 的全部增量来自同一原因。模块快照未见 CUDA 也不能证明 SDK/注入代码从未调用相关接口。

另按 NVIDIA 文档对 `CUDA_FORCE_PRELOAD_LIBRARIES=0` 做进程内环境 A/B/A 筛查，三组仍增长，未进入生产配置，也未更改系统环境变量。
