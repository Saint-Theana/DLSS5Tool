# 双模式调参响应优化（2026-10-10）

## 交付范围

本次针对用户报告的参数拖动、数值调整卡顿，修改开发版 Python/Tk 界面及本地预览调度。
不修改模型、导出算法、原生着色器、实时主机协议或运行依赖；不打包、不发版。
原有未提交的双模式共享改动保留。关闭并重新通过仓库 `run.bat` 启动即可加载本次代码，
已有安装包/冻结 EXE 不会自动获得修改。

## 行为

- 两边共用 ParameterRow：拖动期间只更新滑块和数字，松手一次提交最终值；键盘、数字框、
  百分比、开关、撤销和范围校验保持原契约。减少无变化的变量写入和范围重绘。
- 本地设置读取不再反复写回整组控件；预览轮询/自动保存不会提交仍在拖动的半成品值。
- SR/FG 路径的提交回调不再同步合成整帧。保留 120 ms 合并窗口，依赖已有异步渲染缓存，
  仅 FG 等待时提供后台合成的真实帧；不重复计算 SR-only 的中间预览。
- 普通本地静帧/暂停预览的输出混合、残差及保护区域合成移到后台。每个合成器最多一项运行、
  一项可替换的最新请求、一份当前结果；工作线程不调用 Tk，不降分辨率或计算精度。
- 等待期间保留同一源帧的上一张有效画面，首次无结果则用源图；状态栏提示正在更新、
  已等待时间和可继续调参。完成、失败、换素材、切模式、导出、关闭等不会误回写旧结果。
- 实时拖动期间不整面板重排；状态/安全控制照常轮询，旧请求的回执不能把正在拖动的中间值
  自动提交。保留原有“最新值等待上一请求确认”、超时重试、需重启参数不可自动重启的逻辑。
- 非 SR/FG 本地播放中调整输出外观时，会像基础 NR 调参一样暂停在当前帧，转入后台静帧更新；
  不清空昂贵的推理缓存。SR/FG 的已有异步播放路径保持不变。

### 合成性能探针

无用户媒体、无 GPU 推理。结果为本机单次对照，不是所有硬件的帧率承诺。

| 项目 | 修改前/同步 | 修改后/后台 |
| --- | --- | --- |
| 本地 180 次拖动中整面板刷新 | 180 | 0 |
| 实时 180 次拖动中整面板刷新 | 80 | 0 |
| 本地拖动含 idle 绘制 p95 | 3.84 ms | 2.91 ms |
| 实时拖动含 idle 绘制 p95 | 2.28 ms | 1.20 ms |
| 2176×3840 残差合成阻塞/提交耗时 | 4231.00 ms | 0.25 ms |
| 该合成期间 Tk 心跳 | 停顿 4231.34 ms | 380 次，间隔 p95 12.23 ms，最大 31.64 ms |

同一全分辨率 CPU 合成函数前后逐像素一致；没有把渲染耗时当作加速收益。探针对比的是
“主线程直接调用”与“交给后台”，不代表完整应用/真实游戏的端到端延迟。

## 边界与手动体验

这次优化调参操作，不是提升模型推理速度；没有重新进行真实游戏捕获性能测试或发布包验收。
非 SR/FG 的连续播放合成本身仍是原有实现，不声称所有播放场景完全异步。
建议用实际素材在两个模式各连续拖动数次、数字框连点、松手等待，确认最终画面/数值一致，
等待期间仍可继续操作，撤销正常。需要重启的实时参数仍须显式确认重启。
