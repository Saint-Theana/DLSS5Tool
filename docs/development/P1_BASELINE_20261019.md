# P1：设备对账与小型性能基线 · 2026-10-19

## 结论与建议

本轮只做研究，未修改生产处理链。当前证据不支持“没有使用显卡”；更明确的问题是：

1. **零效果仍付出增强成本。** 在本轮 SDR 合成素材中，`nr_quality.total=0`、四个基础增强参数为 0，均与 `enhance=False` 的纯超分＋插帧输出逐帧一致，但前两者仍各调用 NR 32 次；`total=0` 还执行合成。
2. **暂停预览可能反复支付设备／shader 冷启动成本。** 同样的百万像素合成，短线程每次重建约 219 ms/次，同线程预热后约 11 ms/次。这是隔离合成调用对照，不是整个 GUI 的加速倍数。
3. **选卡契约不统一。** 本机各相关进程确实落在同一张卡；但 NR、VSR、合成、FG、编码采用不同选卡入口，单卡成功不等于多卡正确。
4. **串行处理和帧搬运确实值得优化。** GUI SDR 超分入口同步执行 VSR → NR → 合成 → 编码，增加 NR 在途槽本身不会形成流水线。合成 DLL 调用以外也有明显成本，不能只优化 shader。

建议下一轮先落地**保守的“纯超分／插帧、零效果”旁路**，再做**本地合成显式选卡及其他模块设备约束**、**预览 worker 复用**，最后按实际 GUI 基线减少 CPU 转换／拷贝及评估有界流水线。不先扩大队列、不以 GPU 百分比为验收目标。

本地合成后续功能依赖仍保持：选定 GPU → HDR 公式对齐 → HDR 接入 → 同卡免读回。零效果旁路与预览复用不代表提前接入后面的 HDR／零拷贝工作。

- 源码基线：`6e05ff6`，即 P0 修复提交。发行说明和更新策略存在用户既有改动，本轮不触碰。
- 硬件：单张物理 RTX 4070 SUPER，驱动 617.42，`nvidia-smi` 总显存 12,282 MiB。应用可用适配器列表中只有一项，CUDA 0，PCI `0000:01:00.0`，LUID `00000000:0001358A`。DXGI 原生日志另有同名枚举项，不能将其当作多张物理显卡的实测。
- 复用 `.venv`：Python 3.13.3、NumPy 2.5.2、OpenCV 5.0.0；FFmpeg 7.1.1 full build。不安装／复制环境、模型或 CUDA。
- 输入：32 帧、30 fps、960×540 的移动 `testsrc2`；NR 单独对照使用其 1920×1080 缩放编码版本。输出统一为 1080p H.264 NVENC P5/high；输入无音轨。
- 六种组合各顺序运行两次，第二轮倒序。NR 明确传入应用枚举的适配器 ID，关闭自动回退、guidance/RAFT，单个在途槽。插帧为 2×，空间超分为 2×。
- `gui_sr_nr` 调用真正的 `App._export_sdr_upscaled_video`。其他组合调用现有 `frame_generation.export_video`，**不是普通 GUI 的异步／缓存处理链**；其中 NR 单独对照也包含该通用入口的 scene/proxy 工作。
- 使用独立研究进程临时包装现有函数计时；正式应用代码不变。处理阶段为包含 IPC、同步、上传、读回和调度的**墙钟耗时**，不是 GPU 内核时间。
- 稳态源帧吞吐取第 4 个已完成源帧之后的进度区间；冷启动、收尾及暂停进行的设备清单采样不计入。阶段表取各函数前 4 次调用之后的均值，嵌套计时不可直接相加。
- 每个编码前输出帧额外计算 SHA-256；该审计本身约 2.5～2.6 ms/输出帧，保留在吞吐内，不把含探针开销的数字作为发行性能承诺。
- 最长 120 秒 watchdog，通用入口检查本进程私有提交增量 2 GiB；P0 的生产内存准入同时有效。这不是完整进程树的长期内存压力验收。

## 1. 设备对账

第二轮在第 4 个源帧完成时暂停业务处理，使用 Windows GPU Engine／GPU Process Memory 计数器枚举探针及组件 PID。它证明进程在何处持有 GPU 资源，**不证明处理期间各引擎的占用百分比**。暂停时的 0% 不能用于解释性能。

以 `sr_nr_fg-r2-profile.json` 为例：

| 阶段 | PID | 观测到的 LUID | 专用显存账面字节 |
| --- | ---: | --- | ---: |
| VSR 超分 | 10668 | `00000000:0001358A` | 205,463,552 |
| NR 增强 | 45480 | 同上 | 534,671,360 |
| FG 插帧 | 40336 | 同上 | 350,900,224 |
| FFmpeg/NVENC | 41440 | 同上 | 283,463,680 |

该例主探针 PID 38064 也在相同 LUID 上持有合成资源；NR 会话返回的适配器信息与 FG 握手返回的 LUID 同样一致。NVOFA 与 FG 的物理设备一致性检查未报错。

但是源码契约仍有以下差异：

| 模块 | 当前选择方式 | 本轮能确认／不能确认 |
| --- | --- | --- |
| NR v2 | `ProcessLive` 接收 `render_gpu`，原生宿主按明确 LUID 创建 | 会话返回选中设备；本轮确实匹配 |
| VSR | `native/vsr_host/vsr_host.cpp::CreateDevice` 选择高性能枚举中的首个可用 NVIDIA；Python 初始化不接收所选卡 | 本机资源归属一致；多卡不保证跟随 NR |
| 本地合成 | `native/realtime/quality_bridge.cpp::Initialize` 用空 adapter 创建 D3D11 设备 | 本机归属一致；仍未显式绑定所选卡 |
| FG | `NativeStream` 不传 `render_gpu`，worker 返回所选 LUID；日志为 `policy=auto-nvidia` | 实际 LUID 已返回，不等于按用户所选卡初始化 |
| NVOFA | 现有 CUDA 入口；导出检查其 LUID 与 FG 一致，否则停止 | 不是与 NR／VSR 的全链统一选卡 |
| 编码 | 普通 FFmpeg NVENC 参数不传选定 LUID；另一原生 GPU writer 的 ordinal 默认 0 | 本机 NVENC PID 在同卡；不能外推多卡正确 |

第一轮用系统 Windows PowerShell 子进程读取计数器失败，错误完整保留在 profile 中。第二轮改用已有 PowerShell 7.6.5，六组均取得清单，无采样错误。没有用第一轮的失败遥测宣称完成设备测量。

## 2. 吞吐与阶段耗时

以下都是**源帧/秒**。2× 插帧输出为源帧数的两倍，不能与原始源吞吐混淆。

| 路径 | 第一轮 | 第二轮 | 输出帧数/轮 |
| --- | ---: | ---: | ---: |
| NR 单独对照（通用入口） | 22.78 | 22.79 | 32 |
| GUI SDR：VSR + NR，外观总量 .75 | 14.49 | 13.34 | 32 |
| 通用入口：VSR + NR + FG，外观总量 .75 | 5.77 | 6.02 | 64 |
| 通用入口：VSR + FG，`enhance=False` | 8.89 | 10.04 | 64 |
| 通用入口：VSR + NR + FG，外观总量 0 | 5.84 | 4.40 | 64 |
| 通用入口：VSR + NR + FG，四个基础参数 0 | 8.04 | 6.19 | 64 |

两轮中间存在明显速度变化，尤其 NR RPC 和 VSR；没有足够的同步负载／频率曲线判定变化来自其他 GPU 工作、时钟、电源或其他调度因素，不能给出固定收益比例。一次研究结束后的 `nvidia-smi` 快照为 GPU 2%、210 MHz，它不是上述处理区间的活跃采样证据。

比较稳定、可指导下一步的阶段事实：

- NR 单独对照约 11.7～12.1 ms/调用，GUI 中约 11.8～14.2 ms；组合插帧路径第二轮可升至约 27～52 ms。前后输入／输出共享内存复制合计约 2 ms；RPC 包含宿主处理和等待，不等于纯 GPU 算时。
- GUI 中 VSR 约 6.1～7.0 ms/调用；CPU 解码读取约 1.5 ms/调用，但该读取也不等于完整解码线程成本。
- GUI 的 `compose` 每源帧进入两次：一次带外观参数实际合成，一次由 `compose_output_frame(settings=None)` 立即返回。profile 的 22.1～22.6 ms 是这两类调用的混合均值，折算约 **44～45 ms/源帧**，不能误报为每帧 22 ms，也不是重复执行两遍 shader。
- 实际 GUI 合成 DLL 调用约 4.1～4.7 ms/帧，包含两张输入上传、dispatch、完整读回；调用前后仍有 BGR/RGBA 整帧转换、分配及复制。约 40 ms 的 DLL 外成本值得进一步分解；目前不能把这部分全部归为纯 CPU 计算。
- 通用插帧路径光流约 23.7～27.2 ms/调用，FG 进程处理约 24.3～32.7 ms/调用。二者都包含搬运和等待，不能直接据此选择新光流算法。
- CPU resize 单次约 3.6～5.1 ms，且部分路径每帧调用不止一次。NVENC `write` 返回通常约 0.8～1.1 ms，但管道返回时间不是编码器全部耗时，不能据此断言编码完全免费。
- 冷启动 NR 约 6.1～7.8 秒，VSR 约 1.8～2.3 秒，FG 约 4.0～4.6 秒；VSR 收尾约 3.05 秒。源码确有 3 秒 join 超时，但本轮未跟踪退出握手，**尚未证明必然超时／强杀**。短视频总耗时不能用来估计长视频稳态。

这些结果说明阶段串行、CPU／GPU 往返和生命周期成本需要分别处理；它们还不能重现或定因用户“低占用＋爆内存＋退出无效”的完整故障。

## 3. 零效果对照与旁路边界

各轮都将编码前的 64 张 BGR 原始输出（32 真实帧、31 生成帧、1 末帧保持）与同轮 `sr_fg_only` 按输出顺序比较：

| 对照 | 第一轮差异帧 | 第二轮差异帧 | NR 调用/轮 | 原生合成/轮 |
| --- | ---: | ---: | ---: | ---: |
| `nr_quality.total=0` | 0/64 | 0/64 | 32 | 32 |
| intensity/local_tone/local_struct/skin_struct=0 | 0/64 | 0/64 | 32 | 0 |
| `nr_quality.total=.75`（效果有效） | 64/64 | 64/64 | 32 | 32 |

前两类与纯超分＋插帧的最终 MP4 文件哈希也完全一致，说明该素材下不仅帧数一致，像素和编码结果也一致。四个基础参数为零并不代表 NR 未执行；合成中性直接返回也不代表 NR 中性旁路。宿主始终设置 `DLSSNR.Enabled=1`，现有 `zero_guidance_fast_path` 优化 motion/depth 资源，不是关闭 NR。

建议实现时建立统一的“输出是否确实不依赖 NR”判定，先覆盖普通 SDR 的明确纯超分／插帧意图，并同时避免创建 NR 和不必要的 guidance。**不能把‘某个滑条是 0’直接当成全局禁用条件。**

旁路验收至少要补：输出混合、差值／左右对比视图、非中性细调与保护区域、透明度、切镜、取消及异常、多次开关和恢复增强后的 reset／时序历史。HDR/PQ/HLG/scRGB、真实长视频、GUI 缓存命中／失效未在本轮验证，先不要自动扩展到这些路径。

## 4. 合成生命周期对照

真实 `runtime/dlss5_quality.dll`，相同 1000×1000 RGBA、相同外观设置，每组 6 次，顺序为“短线程／同线程／同线程／短线程”。对照复用 P0 的真实 `LatestPreviewJob` 短线程路径，同线程组直接在同一线程连续调用，不假装已经实现常驻 worker。

| 次序 | 生命周期 | 剔除首个调用后的均值 | 创建/最终销毁 | 最终残留 |
| --- | --- | ---: | ---: | ---: |
| 1 | 短线程 | 218.96 ms | 6/6 | 0 |
| 2 | 同线程复用 | 11.18 ms | 1/1 | 0 |
| 3 | 同线程复用 | 11.13 ms | 1/1 | 0 |
| 4 | 短线程 | 218.89 ms | 6/6 | 0 |

短线程预热后 create 仍约 166～169 ms，首个 native compose 约 41～45 ms；复用线程后 native compose 约 1.8～3.3 ms。这里的整次调用不包含线程退出后 destroy 的约 9～10 ms，因此还不是完整 UI 响应延迟。未在本探针重新比较像素，像素契约由已有 P0 专项验收提供，不冒称新增质量验收。

常驻 worker 应保留 latest-only 的一个在算＋一个可替换请求，空闲时不能保留旧帧闭包；由拥有线程执行清理，并定义空闲回收／显卡切换／尺寸变化／退出行为。不能通过扩大线程池来保留多份设备资源，也不能从 UI 线程直接销毁正在使用的上下文。
