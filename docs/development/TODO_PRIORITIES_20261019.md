## 1. P0：内存上涨、耗尽与资源释放

首轮诊断见 [2026-10-19 P0 内存诊断](P0_MEMORY_DIAGNOSIS_20261019.md)：真实 DLL 的 6 次短线程合成创建 6 个上下文、正常销毁 0 个，进程私有提交逐轮增长；同线程复用对照稳定。优先修复原生所有权，再补系统内存压力保护与完整工作负载验证。单次长视频、同线程批量图片和完整退出后的系统异常尚未确认根因。

后续已完成 [P0 首轮落地](P0_MEMORY_FIX_20261019.md)：真实 DLL 6 次短线程创建／正常销毁改为 6／6，遗留为 0；新增系统 RAM／提交余量保护、有限预读与在途槽、超分内存准入，并覆盖主动清理／退出。以下完整用户场景与进程树采样仍作为后续验收，不将其提前勾选完成。

### 用户反馈证据

- 2026-10-17 21:43：用户称机器有 32 GB 内存，超分运行一段时间后“爆内存”，严重时死机重启；暂停后占用会慢慢下降，询问能否主动释放。
- 2026-10-18 00:01：同一用户补充，图片处理多了也会出现内存慢慢上涨。
- 2026-10-18 21:40：另一用户反馈已勾选显卡但占用上不去，最终“爆内存”，退出也未解决，只能重启。

上述时间来自本轮用户提供的两张评论截图。实际应用版本、任务模式、素材、设置、RAM／VRAM 指标及完整进程树未知。
“爆内存”暂作为故障描述，不能直接等同于显存不足或已经确认的内存泄漏。
暂停后缓慢下降可能与积压工作排空有关，也可能有其他原因，需采样区分。

### 当前源码提供的排查起点

- `app_settings.py` 的 `preview_cache_mb` 默认 8192 MiB，可配置为 256～32768 MiB。预算值本身不能证明发生泄漏；它也不是整个应用的进程内存上限。
- `shared_cache_budget.py` 已有 GUI／模型进程共享账本；`guidance_cache.py` 有受限原始光流缓存；`render_cache.py` 有分层画面缓存。
- `gui.py` 已有 `clear_preview_cache()`、在途任务退休及退出清理；不能把“新增清缓存按钮”直接当成完整修复。
- 图片导出有独立处理入口；`gpu_export_process.py` 有子进程取消与退出逻辑。现有保护是否覆盖用户触发的具体分支仍需检查。

### 待办

- [ ] 先补齐最小复现资料：版本与 lite/full、显卡／驱动及内存、源尺寸／时长／图片数、输出倍率、HDR、光流、插帧、缓存预算、预渲染、触发步骤及诊断日志。
- [ ] 分开测三类场景：长视频超分／导出、反复图片预览切换、批量图片导出；覆盖纯超分、增强及插帧的实际设置组合。
- [ ] 同步记录主进程及子进程私有提交／工作集、系统提交量与上限、独立／共享显存、缓存账面字节、在途帧和队列长度，并标记暂停／清理／取消／退出时间点。
- [ ] 核对预算覆盖范围：源帧、空间处理／增强／输出层、原始光流、显示图像／Tk 资源、HDR 浮点中间帧、读写队列及原生纹理／共享句柄。区分缓存、活跃工作与未释放对象。
- [ ] 若发现生产快于消费或预算漏算，优先补字节预算、有限在途帧及背压；预算给系统、模型和处理峰值预留空间，不仅按缓存条目数估算。
- [ ] 检查图片尺寸／参数切换、异常、取消和退出时的线程、子进程、共享内存及原生会话生命周期；不能仅凭窗口关闭判断全部进程退出。
- [ ] 核对现有清理入口实际释放范围；若无法满足主动释放需求，再扩展其语义。清理须等待正确的消费完成，暂停则保持可恢复的必要状态。

### 验收方向

固定素材、设置及预算，观察预热后内存是否进入稳定平台；重复图片／任务批次不能让空闲基线持续抬高。
分别报告暂停、清理缓存、取消、退出后的占用与残留进程，明确有意保留的缓存和会话。
工作集不必立刻恢复到启动值；应结合私有提交、存活对象及重复运行判断是否释放。
在预设安全阈值内验证内存压力处理，避免以再次触发系统死机作为验收方式。

## 2. P1：GPU 占用低与实际吞吐

已完成 [2026-10-19 P1 小型基线](P1_BASELINE_20261019.md)：六种组合两轮顺序测量，另做真实 DLL 生命周期 ABBA 对照。单卡中各阶段资源均归属同一 LUID；源码的 VSR／合成／FG／编码仍没有统一跟随 NR 的显式选卡契约。基线发现两种零效果组合与纯超分＋插帧逐帧一致，但当时仍执行 NR；短线程合成约 219 ms/次，同线程预热后约 11 ms/次。该轮是优化前的小型研究，不是多卡、HDR、真实长视频或完整 GUI 性能验收；后续落地见下文。

本轮已按维护者要求一次覆盖 SDR、PQ、HLG、scRGB，完成 [统一零效果优化](P1_ZERO_EFFECT_OPTIMIZATION_20261019.md)，没有只给 SDR 加临时分支。区分源帧旁路与宿主零参数数值契约；验证恢复增强时的缓存／时序和超分对比源。285 项不同用例分别验证通过（组合运行 283 通过，2 项 Tk 初始化失败后独立重跑通过），另有 45 帧真实宿主与 9 组真实 SR+FG 对照。下一轮做显式设备约束和预览 worker 复用，再按实际 GUI 成本减少拷贝／转换、评估有内存上限的流水线。

- [ ] 明确用户勾选的是哪项设置，日志确认实际选中／使用的适配器、超分／增强／光流／插帧路径及回退，覆盖多 GPU／核显组合。
- [ ] 对照正确 GPU 的计算、3D、复制、解码及编码引擎，同时记录帧耗时；单个任务管理器图表不足以判定未用 GPU。
- [ ] 内部测量解码、预处理、SR／NR／光流／FG、残差合成、上传／读回、编码、磁盘写入及等待，定位限制吞吐的阶段。
- [x] 实现“只要超分／补帧、效果归零”时的统一旁路，覆盖四种色彩配置、差值／对比、缓存隔离和恢复增强；合成素材验证通过。用户实际设置／长视频继续验收，不把小型对照当作完整复现。
- [ ] 对确认的瓶颈再做改动：CPU 工作和搬运优先减少；队列调整必须有内存上限；设备不一致先做第 3 项。不以盲目增大并发或拉满 GPU 百分比作为目标。
- [ ] 预览合成复用同一 worker，保持 latest-only、有界请求、不保留旧帧；清理、设备／尺寸切换与退出都在正确所有权线程上完成，复验 P0 内存回收。

验收比较同源、同设置下的吞吐、阶段耗时、内存峰值及输出一致性。现有百万像素门槛下的小图走 CPU 是有意设计，不能单凭低占用认定其有缺陷。

## 3～6. 继续沿用本地 GPU 合成交接

详细实现、代码位置及每项检查见 [2026-10-16 本地 GPU 合成 TODO](TODO_LOCAL_GPU_COMPOSITION_20261016.md)。
当前源码只在大尺寸 SDR `uint8` 合成使用 DLL，HDR 保持 CPU 路径；本地 bridge 使用默认适配器并整帧读回。
这为后续优化提供了明确入口，但尚不能据此判定本次内存／低占用反馈的根因。

原交接的顺序不变：**导出选定的 GPU → HDR 公式对齐 → HDR 接入 → 同卡免读回**。
每项随实现补对应定向检查；实时宿主继续使用其现有 GPU 纹理路径。

## 7～9. 后续研究及既有边界

研究依据见 [光流性能与质量 TODO](TODO_FLOW_PERFORMANCE_20260915.md)，其历史实施状态应结合后续接入记录阅读。
