## P0：具体缺口

### 1. 超分构造中途失败，没有覆盖前面已取得的资源

位置：[super_resolution.py](../../dlss5tool/super_resolution.py)，`ProcessSuperResolution.__init__` 的共享内存分配到进程构造，以及 `close()`。

- 输入/输出共享内存、NumPy view、Pipe 和 Process 创建在异常回滚 `try` 之前。
- 第二块共享内存分配失败时，第一块没有主动 `close()` / `unlink()`。
- 在这个半初始化状态调用 `close()`，还会因 `_process` 尚未赋值而抛 `AttributeError`，无法完成后续清理。

探针只真实创建 **256 bytes** 的输入段，注入第二次分配 `MemoryError`：close=0、unlink=0、mapping 仍开着；最后由探针自己的 finally 释放。
实际大图的首块大小随源尺寸增长；异常 traceback 被上层保留时，失败构造对象也可以继续存活。没有制造真实内存耗尽。

建议修复：在第一次资源分配前初始化全部可选资源字段；把分配、Pipe、Process 和启动纳入同一回滚区；`close()` 支持任意部分初始化状态，覆盖尚未移交的子 Pipe 句柄。
验收第二块分配、view 创建、Pipe/Process 创建和进程启动分别失败，已取得资源均被释放，重复 close 幂等。

### 2. 保存的渲染异常栈会继续持有大帧，缓存字节无法反映它

位置：[render_cache.py](../../dlss5tool/render_cache.py)，`RenderSession._produce()` 的 `self.error = error` 和 `close()`。

- 保存完整异常对象也保存 traceback；traceback 持有失败 renderer 的局部变量。
- `close()` 清空画面缓存，但没有清理这个 traceback。
- 用一张 **65,536 bytes** 的合成数组配 weakref 验证：失败后仍存活，session.close 后仍存活，尽管 `session.bytes == 0`；清除保存异常的 traceback 并 GC 后数组回收。

这证明错误状态可以保留缓存账外的帧；不等于证明正常连续处理无限增长，也不等于每次错误都累积一份会话。
本地/共享预览还有其他保存异常对象的入口，实施修复时应核对直接关联的错误展示路径。

建议修复：保留用户错误消息及文本诊断，避免长期保存带活跃帧引用的异常栈；处理 cause/context 链和上游引用；关闭后清空不再需要的错误数据。
验收错误仍可读、失败任务不会被复用，frame weakref 在资源关闭后能回收。

### 3. “一帧也放不下”被重新提升为一个在途槽

位置：[super_resolution.py](../../dlss5tool/super_resolution.py) 的 `select_in_flight()`、[gui.py](../../dlss5tool/gui.py) 的 `_export_hdr_video()`、[dlss_host_process.py](../../dlss5tool/dlss_host_process.py) 的 `_HostSession`。

- `bounded_frame_count()` 明确允许返回 0，表示当前安全余量不足一帧。
- 调用方使用 `max(1, bounded_frame_count(...))` 把拒绝结果提升回 1。
- scale=1 的 HDR 路径不创建 `ProcessSuperResolution`，因此也不会经过该构造器已有的 RAM 准入检查。
- 模拟物理 RAM/提交余量均为 0：选择结果仍是 1，HostSession 到达第一块 **16,588,800 bytes** 的共享内存分配；探针在分配前主动抛错，没有实际分配大帧或启动 GPU。
- 原生 `CreateFrameResources()` / `host_queue::Limit()` 有额外槽数限制，但下限仍是 1；这也不能代替“首帧分配之前”的拒绝。

建议修复：保留 0 的拒绝语义，在 reader/writer/共享内存及模型分配前执行明确准入。除 SR 外覆盖纯 NR/HDR 分支；余量未知时遵循既有策略，余量确定不足时给出可操作错误，不改分辨率、精度或画质。

## P1：全链路设备身份与显存查询

本地 NR 和新合成桥已有显式 LUID 契约，剩余边界如下。

| 模块 | 当前代码事实 | 后续工作 |
| --- | --- | --- |
| VSR | `vsr_host.cpp::CreateDevice()` 按高性能顺序选择首个可用 NVIDIA；Python 会话没有所选卡参数 | 沿用导出实际选定身份，返回并核对实际设备；会话复用键包含设备 |
| FG / NVOFA | `NativeStream` 未传所选 LUID；已有 NVOFA↔FG 同卡检查 | 把选卡贯通到创建阶段，保留已有失败/一致性检查 |
| 原生编码 | `create_video_writer()` / `NativeGpuVideoWriter` 的 CUDA ordinal 默认 0 | 从选定物理身份映射 CUDA 设备，不把 DXGI 枚举序号当 CUDA ordinal |
| 普通 FFmpeg 编码 | 没有统一接收 NR 的显卡选择 | 在明确支持的编码路径传递相同设备意图，保持软件编码与既有格式合同 |
| 资源查询 | `query_gpu_memory()` 只解析 nvidia-smi 输出第一行，缓存也不区分设备 | 按实际身份查询和缓存，用同一设备的空闲显存做风险/队列判断 |

模拟两卡输出：A 空闲 20,000 MiB，B 空闲 500 MiB。对建议显存 3 GiB 的任务，现有查询得到 A 并显示低风险；若任务实际使用 B，对应风险是高。
这是有确定输入的代码复现，**没有宣称真实双物理 GPU 已验收**。

建议先统一 LUID / PCI 或 UUID / CUDA ordinal 的映射与实际回执，再贯通调用链；不存在的显式选择不能静默换卡。缺第二张卡时先验证映射、故障分支与单卡实际身份，多卡留待相应硬件补验。

## P1：HDR CPU 输入准备已经是可量化的成本

位置：[residual_composition.py](../../dlss5tool/residual_composition.py) 的 `_native_inputs()`；传递函数仍复用 [video_export.py](../../dlss5tool/video_export.py) 的 PQ/HLG 实现。

当前路径先把原图和 NR 图各复制为 RGBA32F，再在 CPU 对两份 RGB 做 EOTF，之后上传给 GPU 合成。

本轮独立进程、NumPy 2.5.2、1920×1080 RGBA16F 合成输入；每档一次预热、五次顺序测量。
没有调用 DLL、模型、GPU 或编码器；下面只表示 **两张输入的 CPU 准备**，不是整个导出耗时或加速承诺。

| profile | CPU 准备中位耗时 | 准备后两份 RGBA32F | 单独追踪的新增分配峰值 |
| --- | ---: | ---: | ---: |
| PQ | 275.07 ms | 63.28 MiB | 181.93 MiB |
| HLG | 246.14 ms | 63.28 MiB | 259.12 MiB |

峰值为独立一轮 tracemalloc 记录，含 NumPy 的已追踪分配；不含既有 31.64 MiB 输入帧对、解释器、模型、驱动和 GPU，不作为整个进程峰值。
另一次单独分解：PQ 总 279.00 ms，其中两次 EOTF 共 214.79 ms；HLG 总 249.56 ms，其中 EOTF 共 184.64 ms。分解采样和中位数采样分开，不能把各项直接加到上表。

因此 GPU EOTF 值得优先做受控原型：直接接受原 profile/格式，在线性光 shader 内解码并合成，减少 CPU 大帧暂存及上传字节；保留旧 DLL、故障与 CPU 消费者的回退。
不能靠降低精度、夹掉 scRGB 负值/超白、改变 PQ/HLG 权重或修改输出合同换速度。原型应同时验证 SDR、PQ、HLG、scRGB、alpha、保护遮罩及编码前数值，并以完整调用开销和内存峰值判断是否接入。

## 建议实施顺序与验收

1. **先处理三个 P0 缺口**：把失败回滚、错误数据生命周期、零余量拒绝补完整，再重跑对应模块测试。
2. **P1 先对齐设备与显存身份**：VSR/NR/合成/FG/编码共享明确设备意图，故障可控。
3. **P1 再做 HDR 转换原型**：同源、同设置交叉比较 CPU 准备和候选完整路径，数值/色彩先过门槛，再判断吞吐与内存收益。
4. 完整长视频、反复图片切换和批量图片，补主/子进程及系统提交量曲线，标记暂停/清理/取消/退出。此前“发布后收集用户素材反馈”的安排保留；本轮不把它提前写成验收完成。
