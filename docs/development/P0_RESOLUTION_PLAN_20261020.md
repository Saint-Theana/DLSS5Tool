# P0 内存增长完整解决方案 · 2026-10-20

## 状态与目标

**项目侧显卡探测隔离与生命周期保护已落地，实际验收见 [实施记录](P0_ADAPTER_ISOLATION_20261020.md)。** 随后完成 [换尺寸修补与服务重启对照](P0_COMPLETION_20261020.md)：GUI 30 次图片轮换达到同尺寸门槛，修复后合成器五分钟空闲与三十分钟连续换尺寸均通过本轮门槛；VSR／NR 仍增长，服务重启未消除问题，继续进入下文环境／SDK 对照分支。已有资源所有权、失败退休重试和运行期内存余量保护继续保留，P0 仍为部分完成。

目标是消除已复现的持续原生增长，保留物理显卡选择、输出质量和连续处理时序契约，并分别验证工作进程、GUI 与整个任务的内存平台。驱动/SDK 内部的最终触发责任尚未确认，因此不能预先承诺只修改 Python 即可解决所有场景。

依据：[原生分配定位报告](P0_NATIVE_ALLOCATION_20261020.md)。本机 CUDA 初始化＋D3D11 空计算后空闲约 60 秒，默认原生堆增加约 70.15 MiB；不含 CUDA 的 D3D11 对照约增 0.071 MiB。合成器及最小组合抓到相同 `nvwgf2umx.dll` 分配栈。该证据确认本机触发路径，不能替代原用户 32 GiB 机器的最终验收。

## 一、统一隔离整条显卡探测链

### 修改范围

- 新增最小显卡探测入口，将 DXGI 枚举/能力查询、CUDA 身份查询与两者匹配放在一次性子进程中。
- `dlss_engine.available_render_adapters()` 改为取得探测结果；`_configure_render_adapter()` 复用同一接口，处理进程不再为显卡信息查询调用 `cuInit()`。
- GUI 显卡列表、诊断信息、合成器 `_composition_adapter()` 统一使用该结果，覆盖无 NR 会话时的合成入口。
- NR 已建立会话时，优先传递实际设备身份；现有 `_composition_adapter` 元数据交接继续复用，补齐遗漏入口。

### 接口与生命周期

- 返回可序列化的显卡身份、能力和查询状态；保持现有物理显卡 ID、PCI 身份、当前 LUID 的匹配规则。
- 区分查询失败、没有显卡、显卡已变化三种结果。保留明确的手动选卡语义，目标不可用时报告对应错误。
- 合并同一进程内的并发探测，缓存当前会话结果；显式刷新、设备变化或身份核验失败时失效并重新探测。
- 为启动、读取结果和退出设置有限等待；超时后仅回收该次创建且身份已核实的子进程，回收完成后才允许下一次探测。
- 主程序关闭时回收探测所有者；半初始化、管道损坏、取消、退出失败均有可重试的清理路径。
- 源码运行和冻结程序均有内部探测入口；入口先于 GUI 和处理模块初始化分派，避免递归启动界面。
- 探测进程不创建实际图像处理会话，不导入 Torch/模型，不产生媒体文件。

### 首轮定向回归

覆盖探测成功/失败/空结果、并发合并、缓存失效、超时回收、关闭与取消、损坏消息、冻结入口、两张同型号显卡、驱动分区视图去重、显卡身份变化、自动/手动选择、合成器和 NR 实际设备交接。

复用现有 `test_gpu_adapter_selection.py`、`test_composer_device_and_worker.py` 及相关 GUI 选卡用例，并新增探测所有权用例。依改动范围执行关联测试，无必要不跑全量回归。

## 二、核对真正执行 CUDA/D3D 的处理边界

现有 NR、VSR、Guidance 和 GPU 编码已有进程边界；优先复用并核实其运行内容。

| 路径 | 实施要求 | 验证方式 |
| --- | --- | --- |
| GUI 和本地 D3D 合成 | 接收探测结果及实际选卡信息；查询逻辑不在此初始化 CUDA | 捕获查询执行进程身份、模块/初始化记录与首帧空闲曲线 |
| NR/VSR 工作进程 | 去除显卡查询带来的 CUDA 初始化；记录 SDK 启动后实际加载/调用的组件 | 分别观察首帧前后与空闲增长，不能以树总量替代 worker 本身 |
| Guidance/光流 | 复用现有独立模型工作进程，核对 GPU 共享资源和同步交接 | 按真实物理显卡身份验证导入/释放及顺序 |
| GPU 编码 | 复用现有编码工作进程，核对正常完成、取消和异常时的共享资源回收 | 检查生产者/消费者身份、帧完整性及进程退出 |

隔离进程限制故障影响；每个工作进程自身是否持续增长仍是验收项。若 SDK 自身在同一进程内部启用 CUDA 和 D3D，应用外层的进程划分不能证明该分支已修复，必须进入下文的环境/版本对照。

处理验收使用原有画质、分辨率、选卡及连续时序设置；NR 会话在正常视频处理中保持连续，停止/取消按明确的用户操作和资源生命周期执行。

## 三、保留内存压力下的可靠停止

已有系统 RAM/提交余量、父进程送帧前检查、NR/VSR 活跃及空闲轮询保护属于故障控制。实施本方案时回归这些边界，并在诊断中区分：

- 正常处理与退出；
- 因内存压力停止且正确报告错误；
- 工作进程无响应后由 supervisor 回收；
- 预热后内存达到稳定平台。

压力停止或强制回收不得记为“内存平台通过”。失败清理继续保留可重试的所有者，输出按既有失败事务处理，不把中断任务记为成功。

## 四、对 SDK 内部剩余增长完成环境对照

只有在上述代码候选和普通实际负载已有数据后，才按单变量继续以下对照，避免同时更换多个条件而无法归因。

1. 在当前驱动与浮窗开关状态下，用全新进程运行最小组合及对应 NR/VSR 用例，形成修复后的基线。
2. 保持已关闭的浮窗设置，重启 Windows 后复测，并记录新进程模块状态。重启用于验证环境状态，不能作为已经修复增长的证明。
3. 若仍增长，选择一套支持当前 GPU 与运行时的官方驱动候选，与现有驱动逐项对比；先保存安装来源、当前版本和回滚条件，再进行环境变更。
4. 用同一个最小组合和同一条实际项目路径验证；只有两个用例均有改善，才能将该环境条件登记为有效兼容方案。
5. 若仍定位到 SDK/驱动内部调用栈，整理最小复现、版本/模块哈希、增长曲线和调用栈，明确未通过的路径及支持范围，继续保留 P0 待办。

本方案不预先指定“已修复的驱动版本”，现有证据尚不足以作此结论。系统重启和驱动安装是独立环境操作，不能从代码测试结果推断它们已经执行或有效。

## 五、同一轮实施的验收矩阵

以下为本方案建议采用的验收门槛，不是已经取得的成绩。所有实际试验先检查磁盘/内存余量并登记新任务目录，复用现有依赖；达到安全阈值提前结束并记录失败原因。

| 阶段 | 工作负载 | 通过条件 |
| --- | --- | --- |
| 隔离契约 | 显卡刷新、并发请求、异常/退出、多卡模拟、冻结入口 | 查询只在探测子进程执行；身份匹配正确；无递归启动/残留/无界等待 |
| 空闲平台 | 最小组合、实际合成器、VSR、NR 各首帧后空闲 5 分钟 | 精确 PID+创建时间的私有提交与原生堆曲线进入平台，原先约 70 MiB/分钟的增长消失 |
| 长时平台 | 通过空闲门槛的相关路径进行至少 30 分钟实际连续处理 | 预热后不持续积累；后半段分窗中位数无连续上移趋势；未由压力保护或回收兜底掩盖 |
| 图片/重复任务 | 同一 GUI 进程轮换三种尺寸，完成 30 次预览/导出，另做三次任务结束重开 | 相同任务的空闲基线进入可解释的平台；缓存、Tk 图像及原生对象变化有对应原因 |
| 生命周期 | 处理中取消、暂停、清缓存、初始化失败、退出和重开 | 资源所有者状态正确；该退出的进程、共享内存和句柄均退休；故障可重试 |
| 质量与选卡 | SDR、PQ、HLG、scRGB 及涉及的光流/编码路径 | 按既有输出对照标准通过；实际设备身份与用户选择一致；连续时序正确 |

内存平台判断同时报告预热区间、每个观察窗口、私有提交变化、原生堆变化、过程峰值和退出结果；缓存预算及解释允许的阶跃在运行前确定。单个总差值接近零、工作集下降、进程自然退出或 `passed` 字段不能单独替代平台结论。若曲线仍不明确，则延长该条路径观察，而不是重复无关全量测试。

64 GiB 本机通过后，原用户 32 GiB 长视频/批量图片故障仍需要独立回验；真实 OOM/系统死机不作为实验目标。

## 六、交付与失败分支

同一轮交付应包括：

1. 一组可审查的探测隔离和调用链改动，记录与当前未提交修复的边界。
2. 关联回归结果、探测进程生命周期证据，以及通过门槛的实际负载记录。
3. 修复前后相同输入/设置和运行库的比较，逐轮记录源码/运行库版本及探针限制。
4. 更新后的 P0 清单：项目侧已落地、环境对照已通过、仍受影响路径分别写明，未通过平台验收不标全部完成。
5. 可复用脚本、必要原始证据及临时目录收尾记录。

若第一部分解决 GUI/合成增长、但 NR/VSR 仍增长，先保留已验证的项目侧改善，后两条继续进入 SDK/驱动对照；不能将局部改善写成 P0 全部解决。若代码候选产生选卡/共享资源/输出回归，修正或撤回该候选，并保留已有可靠的生命周期保护。

正式打包按仓库发行与增量包工作流另行执行；方案阶段不把源码修复或有限实测称为已发布版本。
