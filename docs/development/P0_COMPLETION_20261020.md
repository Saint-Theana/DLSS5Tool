# P0 图片内存修补与剩余 SDK 增长核验 · 2026-10-20

## 当前结论

本轮已修补新定位的本地合成换尺寸增长，GUI 30 次图片预览／导出通过原先登记的同尺寸内存门槛。**P0 仍为部分完成**：VSR、NR 工作进程的空闲增长仍存在；授权的 NVIDIA 服务重启未消除它。

修复后合成器的五分钟空闲与三十分钟连续换尺寸均通过本轮门槛。验证过的 DLL 已原样更新到项目 `runtime/dlss5_quality.dll`，原 DLL 保留在本任务回滚目录；这不是正式打包或发布。

## 一、实际落地的代码修补

- `quality_bridge.cpp` 换尺寸前清空 D3D11 状态、释放旧纹理／视图，并刷新延迟销毁，再分配下一组纹理。原先只释放 COM 指针不足以让本机的逐次分配进入平台。
- `ResidualComposite` 将纹理／视图的 `ResetBindings()` 与整个设备资源的 `Reset()` 分开。换尺寸继续使用同一设备的着色器、常量缓冲和计时查询，完整退休仍释放全部对象。
- GUI 导入另一张有效图片时，清除旧帧、请求令牌、输入引用和来源缓存，但复用同一预览线程上的无时序合成设备。清空媒体、主动清缓存、关闭、失败及原有 30 秒空闲清理继续走真实释放；显卡身份变化仍由现有 LUID 契约处理。

没有修改 NR 视频历史、图像质量、实际选卡策略或原有运行期内存余量保护。新用例覆盖执行中换图、同键重新请求、旧结果隔离、正常清缓存及源文件验证失败；原生 GPU 用例覆盖换尺寸后的像素、透明度和计时查询复用。

## 二、定位与候选取舍

### 排除只复用设备的候选

仅让 GUI 换图时复用设备，确实减少了设备创建次数，但原生提交增长更大；该候选未单独交付。其补丁、源码和完整 12 轮测量保留在证据中。

进一步去掉 GUI 和 VSR/NR，仅在同一合成器上交替处理 1920×1080、1600×896 两种尺寸，32 帧仍可复现大幅增长。由此将修补集中到纹理换尺寸的退休和设备资源复用。

| 修改前，32 帧 | 165.78 | 840.47 | 反复换尺寸增长 |

### 三十分钟连续换尺寸

同一工作进程在两种尺寸之间连续切换，完成 94,957 帧。排除前 60 秒后，私有提交的前后分窗中位数差约 +1.13 MiB、约 +0.049 MiB/分钟，五窗中位数范围约 1.51 MiB；后半段分窗差仅 +12 KiB。三项均在原先门槛内，未改阈值。

默认原生堆预热后分窗差约 +0.89 MiB。含预热的完整首尾匿名私有提交差约 +38.55 MiB，不与排除预热后的差值混用。进程树峰值约 225.9 MiB，上下文创建／销毁 1／1、最终设备引用为零，无安全停止、强制回收或遗留进程；所有区域查询成功，测量期间源码和二进制哈希一致。

长测使用任务内候选 DLL，三个 C++ 文件去除行注释和空白后与最终生产源码相同，保留对照哈希。验收后仅从诊断工具撤回未通过恢复检查的实验性虚拟内存追踪，测量源码、变更前后哈希及最小补丁均保存；生产代码未因此改变。最后将同一已验收 DLL 更新到本地运行库，另做实际加载和重开检查。

## 三、剩余 VSR／NR：服务重启的实际结果

测试环境为 RTX 4070 SUPER、驱动 617.42。维护者单独授权当前测试结束后临时重启一次 `NVIDIA Display Container LS`。首次普通权限尝试被 Windows 拒绝；随后经提权，于 03:07:19～03:07:20 UTC 完成一次重启。服务恢复 Running，启动类型仍为 Automatic，未编辑驱动、服务配置或系统启动项。失败尝试与最终成功记录均保留。

重启后以相同生产代码、新进程运行：

| 用例 | 私有提交增长 MiB/分钟 | 结果 |
| --- | ---: | --- |
| CUDA 初始化＋D3D11 空计算，无项目处理 DLL | +38.21 | 仍增长 |
| VSR 首帧后空闲 60 秒 | +39.39 | 仍增长 |
| NR 首帧后空闲 60 秒 | +33.90 | 仍增长 |

同一 GUI 的最后 300 秒空闲也给出独立验证：GUI 主进程下降并稳定，而其 NR、VSR 工作进程分别仍增长约 34.44、36.45 MiB/分钟。两个 worker 的 PID 和创建时间均单独核对；未把后台应用的私有内存合并进来。其他程序仍可能影响驱动状态与调度，这与内存归属是不同问题。

### 短线程与驱动分配证据

新的诊断计数器不挂钩、不分配帧数据，仅计数本测试进程的线程通知，并解析线程入口所在模块。50 个线程的自检记录为 50 次创建／50 次退出。

重启前最小组合 60 秒内新增约 33.5 万个短线程，重启后仍新增约 21.3 万个；绝大多数入口均在 `NvMessageBus.dll + 0x251510`。VSR／NR 的首尾快照也记录到相同模块的大量创建／退出。之前 [原生堆调用栈](P0_NATIVE_ALLOCATION_20261020.md) 已抓到 `nvwgf2umx.dll` 的持续 184 字节分配。

[NVIDIA 开发者论坛的一手复现](https://forums.developer.nvidia.com/t/nvwgf2umx-dll-leaks-184-bytes-per-thread-in-its-dll-thread-attach-handler-595-95-580-88/381379) 同样报告驱动在线程通知中保留 184 字节。结合本机计数与原有分配栈，线程风暴叠加驱动按线程保留是目前较强的解释，**仍不将外部报告当成本机完整因果验证，也未找到已确认修复本机问题的驱动版本**。

重启后的新进程仍加载 `nvspcap64.dll` 和 `NvMessageBus.dll`；主开关关闭及服务重启均未形成完全无覆盖层的对照。GUI 换尺寸增长已用独立合成器定位、修补，不将其归为同一种线程问题。

后续 [原版参考项目同机对照](P0_UPSTREAM_COMPARISON_20261020.md) 在 Veyra 1.4.4 和原始 standalone 中同样复现增长；原版 Veyra 的纯外部 ETW 采集确认同一 `NvMessageBus.dll` 短线程入口。参考增强用例关闭超时保持失败，不能作为平台通过；尚无直接可移植的根治补丁，仍需有效环境／官方驱动对照。

## 四、回归与证据边界

- 本轮关联 Python 回归去重后 220 项均有通过记录；初跑的一项 Tk 初始化失败在独立进程重跑通过，一项旧测试桩缺少实际显卡元数据，补齐契约后重跑通过。原始失败 XML 均保留，不把重跑相加计数。
- 原生 GPU 23 个像素／生命周期用例通过；真实 DLL 四种色彩配置、数据类型和通道顺序的 20 组 CPU 对照通过，透明度保持，未放宽原有误差门槛。
- SDR、PQ、HLG 的真实 GPU 输出到隔离 NVENC 交接各完成 6 帧，GPU 路径没有 CPU 读回，解码后的对照输出一致。
- 已验收 DLL 原样更新到本地 `runtime/` 后，默认加载路径的 32 帧交替尺寸检查及三次独立 GUI 任务重开全部完成；每次重开处理两张图片并完成导出、清缓存和退出。四组均核对确实加载项目 `runtime/dlss5_quality.dll`，源码／运行库前后哈希一致，无安全停止、强制回收或残留。这些短测只验证实际加载与生命周期，不替代正式长测。
- 一个 GUI 诊断因 Windows Python 3.13 的 ctypes 库名参数失败，修正后重跑；虚拟内存 IAT 跟踪有一轮在退出阶段仅恢复 16／22 个槽，因此该轮保持失败，不能充作平台验收。跟踪只覆盖部分入口，也不能解释所有匿名分配；该实验实现已从最终诊断工具撤回，原始证据与源码继续保留。

全部为 64 GiB 本机的本地合成样本。原用户 32 GiB、原始完整素材、小时级负载及真实多卡仍待回验；压力停止和进程自然退出都不算内存平台通过。
